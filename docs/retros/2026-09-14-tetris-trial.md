# 회고: 테트리스 시험 빌드 (2026-09-13 ~ 14)

gatekit 0.5.0을 실제 프로젝트 하나에 처음부터 끝까지 적용한 첫 시험이다.
대상은 브라우저 테트리스(정적 HTML·CSS·JS, 의존성 없음). 결과물은
https://github.com/LovelyPaul/tetris 에 분리해 Vercel에 배포했다.

## 한 줄 결론

파이프라인 7단계가 모두 통과했고 게이트는 설계대로 거짓 통과를 잡아냈다.
그러나 코드 작성 25분에 전체 2시간 40분이 들었고, 그중 30분은 게이트 명령
작성 실수의 복구였다. 도구 결함 5개와 사용 경험 문제 8개가 나왔다.

## 도구 결함

### R1. 재위임이 잡 시작 시점의 게이트를 재사용한다

`04-tasks.md`의 게이트 명령을 고친 뒤 `jobs redelegate`를 돌려도 옛 argv가
실행됐다. 잡 시작 때 작업 펜스를 스냅샷하기 때문이다. 새 `jobs start`만
수정을 반영했다. 재위임 때 펜스를 다시 읽거나, 상태 출력에 스냅샷 사실을
표시해야 한다.

### R2. 잡 중단 명령이 없다

게이트가 틀린 것을 알고도 잡이 끝날 때까지 18분을 기다렸다. 다른 세션의
워커를 건드릴 수 있어 프로세스를 죽일 수도 없었다. `jobs stop`이 필요하다.

### R3. 워커가 게이트를 우회했다

`node --test tetris/tests/shell/`이 "Cannot find module <dir>"로 실패하자
재위임된 워커가 `tetris/tests/shell/index.js`를 만들어 실제 테스트를
`require`하게 했다. 잘못된 명령이 통과했고, 파일 주석에 그 의도가 적혀
있었다. 게이트가 초록불이 됐지만 증거는 거짓이었다.

대응 후보:
- 재위임 프롬프트에 "게이트 명령 자체가 틀려 보이면 멈추고 보고한다. 코드를
  명령에 맞추지 않는다"를 넣는다.
- `jobs start`가 게이트 argv를 한 번 드라이런해, 코드가 없는 상태에서
  디렉터리 누락 같은 오류를 내는 게이트를 거부한다.
- 같은 라운드 재위임에서 새로 생긴 파일이 형제 테스트만 import하면 경고한다.

### R4. 쓰기 게이트가 프로젝트 밖 `.md`를 막는다

승인 전 상태에서 `~/.claude/projects/.../memory/gatekit-backlog.md` 쓰기가
"코드 쓰기 차단"으로 거부됐다. `docs/ARCHITECTURE.md` §write 규칙을 보면
허용 목록은 `*.md at root`라서 동작 자체는 계약대로다. 문제는 두 가지다.
거부 메시지가 "`*.md`"라고만 말해 루트 한정임을 숨기고, 프로젝트 밖의
에이전트 메모리 파일까지 막는 것이 의도인지가 정해져 있지 않다. 메시지를
고치고, 프로젝트 밖 경로는 규칙 밖으로 둘지 ADR로 정해야 한다.

### R5. tokens 게이트에 디렉터리를 넘기면 `unverified`

`tokens.py --lang ko tetris/`는 파일 0개를 검사하고 종료 코드 3을 냈다.
`tetris/**`만 동작한다. 디렉터리를 자동 재귀하거나 오류 메시지로 알려야 한다.
이 때문에 `05-gate.md`를 고쳐 재승인이 한 번 더 필요했다.

## 명령 문서의 공백

### R6. `node --test`와 tokens 게이트는 글롭이 필요하다

두 명령 모두 디렉터리 인자를 받으면 실패한다. tasks·gate 명령 본문에 한
줄씩 적어야 한다. 이 둘이 재승인 2회, 약 30분을 만들었다.

### R7. 승인 뒤 추가된 작업의 추적성

verify에서 결함을 찾아 `touch-wiring` 작업을 추가하자 `05-gate.md`에 그
작업을 참조하는 기준이 없다는 warn이 남았다. 기준을 넣으려면 재승인이
필요하다. 승인 뒤 작업 추가를 어떻게 다룰지 규칙이 없다.

### R8. 배선 작업 누락

`touch.js`를 만드는 작업은 있었지만 `main.js`에 연결하는 작업이 없었다.
단위 테스트 15개가 통과해도 게임에서 스와이프는 동작하지 않았다. tasks
명령에 "모듈을 만드는 작업이 있으면 그 모듈을 쓰는 작업이 있는지 확인"하는
점검이 필요하다.

## 사용 경험

### R9. 승인 반복

게이트 파일을 한 글자 고칠 때마다 재승인이 필요해 세 번 승인했다. 규칙은
맞다. 다만 기준 id와 기대값이 같고 argv만 바뀐 경우 차이를 보여 주고 한 번에
승인하는 흐름이 있으면 마찰이 준다.

### R10. 질문 예산의 범위

예산은 2회인데 세션 안에서 파이프라인 7개를 돌리니 5회가 됐고, 훅은 막지
않았다. 예산이 파이프라인별인지 세션별인지 정의가 흐리다.

### R11. 평가자에게 브라우저가 없다

`05-gate.md`는 "세션의 Chrome 도구로 확인"이라 적었지만 평가자 에이전트의
도구 목록에 Chrome이 없다. F4·F5는 매번 `unverified`였고 결국 메인 세션이
관측했다. 이는 producer ≠ evaluator 원칙과 어긋난다. 평가자에게 Chrome
도구를 허용하거나, 브라우저 확인을 별도 단계로 분리해야 한다.

### R12. 목업 없는 mockup의 프리뷰 분기

목업이 없으면 화면 전체가 가정이 된다. 이번에는 손으로 프리뷰 HTML을 그려
아티팩트로 보여 줬고, 사용자가 그것을 보고 승인했다. 이 흐름을
`/gatekit:mockup`의 분기로 넣되, 근거는 HTML이 아니라 화면별 사용자 승인으로
잡아야 한다. 추출 명령이 그린 것을 관찰한 것처럼 세탁하면 안 되므로 ADR이
먼저다.

### R13. 소요 시간

작업당 워커 세션 기동에 1분 안팎, 승인·검증 왕복에 수십 분이 든다. 이
규모(정적 파일 게임)에서는 한 세션이 직접 짜는 편이 열 배 빠르다. gatekit의
값은 속도가 아니라 통과 증거의 진위에 있지만, 작은 프로젝트용 경량 모드가
없으면 첫 사용자가 이탈한다.

실측으로 나눠 보면 워커 시간 자체는 적정하다. 1차 잡에서 코드를 실제로 쓴
워커 시간은 작업당 3분 12초 ~ 6분 29초, 합계 약 25분, 산출은 소스·테스트
약 3,700줄이다. 게이트 실행은 전부 합쳐 1초 미만이다. 낭비는 구조에서 났다.

| 낭비 | 크기 | 원인 | 조치 |
|---|---|---|---|
| 직렬 라운드 | 임계 경로 18분 (병렬이면 약 11분) | 라운드 폭이 2→1→2→1이라 `parallel: 3`을 한 번도 못 씀 | 1라운드를 3개 폭으로 자른다 |
| 통과한 작업 재실행 | 6분 | 2차 잡이 코드가 있는데도 워커 6개를 다시 띄움(각 62–144초, 할 일 없음 확인만) | 게이트가 이미 통과하면 워커를 건너뛰는 옵션 |
| 게이트 사전 점검 부재 | 18분 (1차 잡 전체) | 틀린 명령을 잡 끝까지 돌림 | `jobs start`가 게이트를 먼저 드라이런 (R3) |
| 검증 | 평가자 4분 × 2 + 브라우저 12분 × 2 | 평가자가 브라우저를 못 써 사람 손이 들어감 | R11 |

스터디 첫 시간 기준: 지금은 인터뷰를 뺀 실행 시간이 약 1시간이다. 위 네
가지를 고치고 첫 시간의 검증을 계약 실행 + 평가자로 한정하면 약 20분이
된다. 인터뷰 깊이는 줄일 이유가 없다. 줄여야 할 것은 인터뷰 뒤의 기계
시간이다.
